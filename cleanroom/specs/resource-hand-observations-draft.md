## Наблюдаемая последовательность сбора

1. Начало locked select выдаёт до25 единиц, ограниченных доступным ресурсом.
   Нулевой запас не создаёт удерживаемый pot. Успешная начальная порция
   списывается из источника и создаёт соответствующий food/wood pot в руке.
2. Пока interaction активен, он увеличивает уже удерживаемый pot того же
   типа. Самостоятельный pot другого типа и сам источник не являются
   допустимой парой для этого продолжения сбора.
3. Каждая очередная порция ограничена доступным количеством источника и
   свободным местом до20000 в удерживаемом pot. Пустой источник/полная рука
   не выдают следующую положительную порцию и прекращают pickup effect.
4. Окончание locked select останавливает continuous pickup effect. В этой
   ветке удерживаемый pot не удаляется и его запас не возвращается в склад.
   Отпускание Action после сбора оставляет ресурс в руке.
5. После сбора рука переходит к обычному состоянию удержания. Сам визуальный
   update мультисбора выбирает hand-spec slot9, то есть hold_side. Это
   отдельное состояние: normal hover не должен немедленно его заменять.

Последовательность подтверждается STATIC-A/B/C и исходными help IDs.
Повторное Action при удержании — действие размещения/применения либо начало
жеста броска в зависимости от движения и цели. Нельзя определить весь ввод
только одной кнопкой clicked в конце кадра. Физическая default кнопка мыши
ещё не подтверждена: `$m2` в текстах — токен подсказки, не самостоятельное
доказательство конкретного mouse button enum.

## Темп и проверяемые числа

При elapsed n игровых turns доля разгона r ограничивается0..1:
`r = clamp(n / (turns_per_second * 6), 0, 1)`.
Запрошенная очередная порция — целая часть `8 + (70−8)*r²`.
Установленная бинарная инициализация —100ms/turn, то есть10turns/sec и60
turns разгона. Время разгона берётся из hand-record; не из частоты кадров.
Высокий FPS не должен увеличивать количество выданного ресурса.

Статически вычисленные fixtures для положительных порций и достаточного
запаса; **не снятые измерения оригинала**:

| n, elapsed turns | n/10 секунд | Запрошенная порция в этот turn |
| ---: | ---: | ---: |
| 0 | 0 | 8 |
| 10 | 1 | 9 |
| 30 | 3 | 23 |
| 60 | 6 | 70 |
| 100 | 10 | 70 |

Если новый контракт определяет начальную25 в момент begin, а последующие
tick callbacks идут с n=1,2,...,N, суммарно в руке:108 приN10;413 приN30;
1746 приN60;4546 приN100. Первые10порций:8,8,8,8,8,8,8,9,9,9.
Это явная convention для fixtures; точное совпадение первого ProcessInInteract
с begin/tick границей оригинала ещё не измерено. Не выдавать эти суммы за
доказанную timestamp последовательность настоящего ввода.

Evidence: STATIC-A/B, DATA-A, BINARY-SCALARS-A. Расчёт выполнен независимо
рациональной арифметикой; возможные крайние различия x87/float32 у границы
целого при других параметрах здесь не исследованы.

## Количественный перенос и видимый поток

В исследованном пути продолжения сбора в одном game-turn сначала вызывается
изъятие из источника, затем фактически изъятое количество добавляется в hand
pot. Обычный hand pot изменяет количество непосредственно в этом вызове.
Не найден отдельный количественный объект «каждая летящая частица» в этом
пути. Количественный перенос здесь синхронный, визуальный поток — отдельный
particle effect. Нельзя автоматически задерживать credit до визуального
прибытия и называть такую политику точной копией оригинала.

Для pickup запускается отдельный PSys effect. Типы для обычной еды и дерева
различаются; у еды есть дополнительный вариант состояния. В данных вызова
создания численные particle IDs107..110 для pickup,111..113 для putdown.
Putdown сохраняет положение руки при старте и отдельный численный параметр.
Само существование этих эффектов не устанавливает их точные траектории,
длительности, частоту частиц, модели/текстуры или правила исчезновения.

Окончание сбора выключает continuous pickup emitter/effects и связанные
звуковые/immersion состояния. Оно не является второй экономической
транзакцией и не должно возвращать или повторно прибавлять уже взятый запас.

Evidence: STATIC-A/B/C/D. Конкретный particle format и visual motion пока
не восстановлены. Допустимо отдельно выбрать явную политику ремейка, например
показывать неколичественные фрагменты при синхронной транзакции; нельзя
одновременно суммировать те же единицы в руке и второй раз как economic flight.

## Размещение и получатель

При применении удерживаемого pot к объекту сначала проверяется, является ли
цель resource store нужного типа; затем используется её resource-receiver
action. При успешном обычном применении получатель получает количество в
вызове AddResource, применённый pot удаляется. Поддерживается также
применение к другой куче/поту того же resource type.

При размещении по земле система сначала ищет подходящие nearby resource
receivers/кучи того же типа. Остаток может стать отдельной наземной кучей
при допустимом месте. Значит пустое место не обязано уничтожать ресурс, а
попадание по исходной storage pile может маршрутизироваться к её зданию.
Не использовать чисто декоративное исчезновение модели как выполненную
доставку. У original-получателей и специальных sites есть дополнительные
условия; все receiver-типы и реакция на частичный отказ здесь не установлены.

Evidence: STATIC-B/C/D. Общую обработку переполнения/частичного приёма и
конкурирующих покупателей надо явно закрепить новым API и tests, сохранив
остаток в руке/мире. Наблюдённый обычный pot pathway нельзя без проверки
обобщать на всякий object, уничтожение source или сетевой rollback.

## Неизвестное и границы будущего packet

- Реальная физическая привязка Action и допустимость движения камеры при
  locked pickup требуют отдельного исследования/оригинального input теста.
- Точный hand-pot scale, пальцевой anchor, качание/переходы и кадры полёта
  particle effects требуют real render comparison.
- Конкретные source-pile выбор/выдача и взаимодействие с concurrent builders
  должны проверяться через настоящее родительское storage, без второго кошелька.
- Большой delta, NaN/Inf, удаление источника/получателя во время визуального
  эффекта, отмена кадра и повторный release — обязанности нового Godot API.
  Оригинал работает turn-обновлениями; поведение arbitrary huge frame delta
  этим статическим разбором не определено. В packet их надо пометить policy.
- Не определены точные полные receiver/throw/aftertouch mechanics. В момент
  броска объект получает скорость непосредственно; скрытый throw animation
  timer не следует придумывать как предварительное условие передачи тела.
- Это исследование не закрывает BW-002 и не подтверждает ручное прохождение.

Минимальные meaningful tests будущего API: пустой источник; нехватка25;
одинаковый итог при разном render FPS; ограничение20000 без потерь; отпускание
останавливает сбор с сохранением hand stock; повторное освобождение не
дублирует credit; quantity-preserving применение/земля; concurrent builder
расход; прекращение source не уничтожает уже held stock; смена hover не
сбрасывает active hand action; particle presentation не меняет учёт повторно.
