# Разделение исследования и новой реализации

## Фактический статус

Ghidra анализирует бинарные программы; она не изолирует людей, ИИ, память
или файлы. Новый чат, subagent, worktree и переименование декомпилированного
кода сами по себе не образуют чистую комнату.

В текущем репозитории уже есть код и заметки с использованием исследований
оригинала и bw1-decomp. Они сохраняются как legacy, без заявления о доказанном
clean-room происхождении. Ниже задан процесс для **новых модулей**, а не
переименование истории проекта в чистую реализацию. Бесплатность проекта
и зависимость от оригинальных файлов эту историю происхождения не меняют.

## Роли и доступ

| Роль | Допустимые входы | Результат |
| --- | --- | --- |
| Исследователь | Собственная установка, Ghidra, поведение оригинала, закрытые research-материалы | Наблюдения, случаи проверки и функциональное описание |
| Рецензент спецификации | Закрытые доказательства и draft спецификации | Проверенный packet без исходного/decompiler кода |
| Изолированный реализатор | Только approved packet, чистый API, синтетические fixtures и инструменты Godot | Самостоятельный новый модуль и tests |
| Координатор/интегратор | Основной checkout/history, утверждённые packets, полученные модули | Адаптеры, проверка настоящей игры и Git-доставка |

Исследователь не пишет продуктовую реализацию исследуемого модуля. Реализатор
не получает binary, Ghidra project, pseudocode, disassembly, чужую декомпиляцию
или legacy-реализацию того же поведения. Уточнения передаются как вопросы
к контракту и новая проверенная версия packet.

## Граница среды

1. Research находится отдельно, например `C:/BW-CleanRoom/research`.
   Там остаются оригинальный exe, база Ghidra, annotations, raw exports,
   логи и доказательства с адресами. Это не папка реализатора.
2. Реализатор запускается в отдельной VM/контейнере/учётной записи с реально
   ограниченным доступом. Внутри только approved packet, пустой проект/чистые
   stubs и необходимые инструменты. Не монтируются оригинальная установка,
   основной checkout, его .git, research/build, домашняя папка исследователя,
   общие чаты, browser sessions, MCP, memories и каталоги журналов.
3. Закрываются пути получить основной repo/декомпиляцию через сеть и общие
   коннекторы. Общие credentials/clipboard не передаются. Нужные официальные
   документы и инструменты можно подготовить отдельно.
4. Нужна свежая сессия с чистой памятью, без fork разговора исследователя
   и без его summary. Обычный subagent может читать те же файлы и автоматически
   загрузить проектные инструкции. Параметры контекста не заменяют OS-границу.
5. В packet копируется `cleanroom/templates/IMPLEMENTER_PROMPT.md` как
   отдельная локальная CLAUDE.md. Основные CLAUDE.md/AGENTS.md,
   HANDOFF_RU.md, BUGS_RU.md и REMASTER.md туда не копируются: они содержат
   legacy/research-сведения. Полный clone основного Git тоже не передаётся.
6. Записываются manifest входных файлов с SHA256, инструменты, роль/сессия,
   границы доступа. Проверяются mounts, history, коннекторы и автоматически
   подгруженная память; одна запись «не читать» технически ничего не запрещает.

Если разделение не обеспечено, укажи это в STATUS и не приписывай модулю
независимое clean-room происхождение. Подготовка среды и исследования остаются
конкретными шагами задачи, но не подменяют готовую игру.

Отсутствие комнаты блокирует именно независимую реализацию, а не всю работу:
координатор продолжает воспроизведение, диагностические tests, проверку сборки,
подготовку API/fixtures и исследовательского packet. Не превращай настройку VM
или обзор инструментов в итоговую сдачу вместо назначенного исправления.

## Утверждённый packet

### Вариант без компьютера у реализатора: одноразовая remote-модель

Вместо VM допускается фиксированный одноразовый запрос к удалённой модели,
которой технически не предоставлены инструменты компьютера. Это граница
доступа самой модели к данным, а не заявление об OS-песочнице локального
координатора. Локальный broker имеет свои обычные права и транспортную
авторизацию, но передаёт модели только утверждённый packet и явную инструкцию.

Проверенный 7 ноября вариант Claude CLI2.1.311: свежий пустой cwd вне repo,
safe-mode и restricted, tools=[], MCP=[], запрет команд/skills/hooks/memory,
явный system prompt, один turn без resume и сохранения сессии. Модель
возвращает текст/код; она не читает файлы, не выполняет его, не вызывает
subagents/браузер/сеть. Код проверяет и запускает отдельно координатор.

Перед применением нужны отрицательный canary-проход и положительный контроль,
проверка init/tool-use/result и SHA256 всех переданных файлов. Проверенные
probes отличили подавленный user/project CLAUDE-контекст от реально загруженных
canaries в контрольном режиме. Одних инструкций «не читать» недостаточно.
Изменение версии CLI/режима требует повторить probes.

Допустим служебный контекст провайдера: имена builtin-компонентов и аккаунтная
метаинформация CLI. Он фиксируется по типам полей без публикации значений;
не допускаются данные игры, repo/history, прежние исследования или память.
Builtin-имена не означают разрешение вызова: tools и фактические tool calls
должны оставаться пустыми. Такая запись не называется «только packet», если
служебная оболочка присутствует, и не сертифицирует legacy-код задним числом.

Авторизация остаётся в единственном штатном хранилище CLI. Не клонировать
OAuth refresh state между broker-запусками; credentials не входят в packet,
ответ, публичный manifest или Git. Запрос, ответ, hashes и список capabilities
сохраняются как локальные доказательства, sanitized manifest — в Git.

Шаблон — `cleanroom/templates/BEHAVIOR_SPEC.md`. Передавай:

- ID/version, область поведения, публичный API, единицы, координаты, условия
  вызова, владельцев состояния и событий.
- Входы/выходы и внешние переходы: когда прекращается сбор, куда относится
  порция ресурса, когда она списана, когда предмет получает скорость.
- Воспроизводимые входные сценарии, ожидаемые результаты, границы/допуски,
  неизвестные факты. Новые требования ремейка отделяются от оригинала.
- Синтетические данные и tests наблюдаемых результатов. Наблюдения имеют
  opaque evidence IDs; адресная привязка остаётся в закрытом журнале.
- Реальный review, авторов ролей и manifest утверждённой версии.

Не передавай построчный перевод, branch layout декомпилятора или макет кода,
переписанного другими именами. Числа/формулы допустимы как проверенные внешние
свойства/формат данных с описанием наблюдения; не выдумывай измерение.
Одно слово APPROVED без выполненного review не утверждает спецификацию.

Полученный новый модуль интегрирует координатор. Он отдельно пишет адаптеры
к существующим загрузчикам и проверяет реальные ресурсы/input. Это не делает
весь main.gd чистой реализацией. Если требуется убрать исследованную legacy-
реализацию системы, её заменяют тем же раздельным процессом, не сертифицируют
старые строки задним числом.

## Ghidra: рабочий путь

Первичные источники:

- [Официальный репозиторий и установка](https://github.com/NationalSecurityAgency/ghidra).
- [Getting Started](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/GettingStarted.md).
- [Headless Analyzer](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/RuntimeScripts/support/analyzeHeadlessREADME.md).

Бери готовый официальный release, а не Source Code archive. Зафиксируй версию
и хеш; JDK выбирай по Getting Started именно этого release. Проверенная
6 ноября 2026 master-документация указывает JDK 25; для другой версии требования
могут отличаться. Собирать саму Ghidra из исходников для задания не требуется.

Headless-шаблон Windows ниже; замени placeholders реальными путями. Найди
actual exe выбранной установки и вычисли его хеш. Старые адреса нельзя
применять к другому binary без проверки.

```powershell
$ghidraPath = 'C:/Tools/<installed-ghidra-release>'
$originalExe = 'C:/<actual-original-game-executable>.exe'
$researchPath = 'C:/BW-CleanRoom/research'
New-Item -ItemType Directory -Path $researchPath -Force | Out-Null
Get-FileHash -LiteralPath $originalExe -Algorithm SHA256
& "$ghidraPath/support/analyzeHeadless.bat" `
    $researchPath 'BWResearch_<binary-hash-prefix>' `
    -import $originalExe `
    -log "$researchPath/analysis.log" `
    -scriptlog "$researchPath/scripts.log"
if ($LASTEXITCODE -ne 0) { throw 'Ghidra analysis failed; inspect its log' }
```

PE loader/language, разрядность, image base и ABI проверь после импорта;
не навязывай guessed processor/compiler spec. Не держи этот project открытым
в GUI параллельно. Для существующего import используй -process вместо
повторного -import. Для automation — -scriptPath и -postScript с именем скрипта;
точные параметры сверяй с официальным README выбранной версии.

Журнал: хеш exe, Ghidra/JDK, команда, import result, реально исследованная
область, проверенные запуском оригинала наблюдения, неизвестные факты и packet.
Выводы декомпилятора о типах/структурах остаются гипотезами до проверки.
Изучай текущую неопределённость, не выгружай весь exe в LLM или Git. Raw-дампы
и проекты Ghidra остаются в research; одного успешного import недостаточно,
чтобы заявить восстановление поведения функции.

## Учёт

В `cleanroom/STATUS.md` отражается действительный прогресс. При первоначальной
передаче 6 ноября Ghidra ещё не запускалась. 7 ноября установлена portable
toolchain и успешно импортирован настоящий exe; отчёт —
`cleanroom/research-status-2026-11-07.md`. Import не означает восстановление
механик. Последующие bounded storage-проходы и новые reviewed packets отражены
в `cleanroom/STATUS.md`; для каждого модуля отдельно записаны доступ и validation.

Для Claude Code сверяй [проектные инструкции](https://code.claude.com/docs/en/memory)
и [subagents](https://code.claude.com/docs/en/sub-agents). CLAUDE.md направляет
работу, но не является принудительным ограничением доступа к файлам.
